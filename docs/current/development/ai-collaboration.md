# 决策、规划、实现与整合协作

状态：用户已明确指定协作分工；执行方法由规划者在授权范围内落实。更新日期：2026 年 10 月 25 日。

阅读时机：提出新需求、制定工作批次、给其他 AI 派工、接收交付及整合成果时。配合 [Git 工作流](git-workflow.md) 与 [工作台账及模板](../../work/README.md) 阅读。

## 三种角色

| 角色 | 负责 | 交付 |
| --- | --- | --- |
| 用户 | 提出目标、补充使用情境、决定影响产品范围/体验/数据的选项，并验收 | 明确的选择和反馈 |
| 规划整合者（当前主会话） | 辅助比较与决策、维护总体设计与当前文档、拆任务、提供提示词、协调接口与依赖、审查及 Git 整合 | 决策说明、批次计划、任务卡、整合报告 |
| 实现者（用户另开的一个或多个 AI 会话） | 在指定工作树中实现获分配的任务、补充必要测试及局部文档 | 代码提交、PR、验证证据与交付报告 |

主会话默认以规划和总体维护为主，不在尚无新需求和决策时自行启动下一批功能实现。整合中可以修复局部兼容、冲突和验证问题；较大功能改动重新拆任务。用户可以在具体请求中调整分工。

该分工不意味着所有读取 AGENTS.md 的 AI 都只做规划：实现者依据任务卡执行代码工作。用户负责启动其他会话；没有具体授权时，规划者不自动新建会话、派出子代理或给其他会话发送消息。需要用户转交的问题和修复要求提供为可复制提示词。

## 从一个要求到一批工作

1. **明确需求。** 查当前记录，区分已确认项、建议、待选项及实现事实。已有答案不重复问；影响产品行为、接口兼容或数据处理的分歧，给出推荐与影响，请用户选择。局部可逆工程细节说明假设后推进。
2. **保存决定。** 更新 `docs/current/` 对应依据及必要的决策记录；未确认的方案留在 `docs/design/`。不要把一份新计划视为用户同意所有开放问题。
3. **制定批次。** 在 `docs/work/` 建立具体批次文件夹，写清范围、非目标、验收标准、接口、文件负责人、任务依赖及 Git 目标。模板见 [批次计划](../../work/templates/batch-plan.md)。
4. **形成派工基线。** 先将供实现使用的决定、契约和任务卡合入 `main`，记录该提交作为派工基线。依赖契约仍未落实的任务不抢跑；研究任务可以先做。实际实现任务不以只存在本会话中的口头方案为依据。
5. **发给用户提示词。** 每个任务给出一段填好任务卡路径的提示词、建议启动顺序、是否可并行。用户在 Codex 选择仓库、工作树模式和约定基线，分别启动实现 AI。
6. **收集成果并整合。** 用户把交付信息带回主会话；规划者检查实际提交并按 Git 工作流合并，更新全局文档和批次结果。

无需固定 AI 数量。能独立验收的任务可并行；同一个大文件、同一接口或迁移链需要频繁协调的工作通常合并成一项，或者先完成公共前置任务。宁可少开一个工作树，也不把耦合隐藏在多个提示词中。

## 每批必须提前说明的边界

- **文件归属：** 每项任务列出允许修改的文件/目录；`shared/contracts`、根 `package.json`/锁文件、迁移清单、AGENTS.md 和总索引指定唯一负责人。并非永久禁止改，而是批内协调修改。
- **插件边界：** 前端 UI、后端业务和设备能力继续遵守 Cordis 服务契约与生命周期。任务独立不代表另建框架或复制业务规则。
- **接口约定：** 输入输出、错误、认证、版本及数据行为须可供各方使用；先落实契约，再并行供给端与消费端。临时替身必须明确仅用于开发/测试，联合验收前验证真实链路。
- **兼容与数据：** 涉及 schema、迁移、回收站、附件保留及备份的改动，需明确已有数据处理与失败恢复；不能由实现者擅自丢弃原数据解决问题。
- **验证：** 指定可观察的结果和相关检查；单任务通过后仍需组合验证。不得把 Windows 实测推导为 Linux/Android 已验证。
- **运行隔离：** 工作树不隔离端口、操作系统资源和用户目录。各任务使用独立样本数据与运行配置，不改其他会话正在使用的环境。

## 用户怎样使用这套流程

可以直接向主会话提出下一项需求，例如“下一步完善记录编辑与回收站，请先协助我明确交互，再拆分任务”。规划者先完成相应决策和计划，随后交付具体任务提示词，不自动把这个例子当作已授权开发任务。

给实现 AI 的提示词由 [任务卡模板](../../work/templates/task-brief.md) 生成；主会话会填好实际任务路径、范围与验收项，用户不必自己拼接设计。第一次启动应确认任务卡已经包含在所选 Git 基线中。

一批完成后，将各实现 AI 的交付报告转交主会话，或使用下面这段提示词：

```text
请作为 Recorder 的规划整合者，整合这一批工作。
批次计划：<仓库内批次计划路径>
各任务的 PR 链接，或分支名 + 完整 HEAD + 本机工作树路径：<逐项填写>
补充：<哪些仍在运行、哪些已停止；已知失败、未提交内容、用户验收反馈>

请先读取 AGENTS.md、Git 工作流与批次计划，核对实际提交和工作树状态。
按依赖顺序审查、解决冲突、验证组合结果，通过 PR 合并，更新当前文档与批次台账。
保持用户现有资料和其他 AI 的未提交成果；涉及新的产品或数据决策先向我说明。
完成后报告主分支提交、验收结果、遗留事项及可清理的工作树。
```

同一台电脑的工作树可由规划者检查共享仓库中的分支和提交；其他电脑的成果须先推送任务分支/PR，或者另行提供可获取的 Git 提交。主会话无法仅凭“另一个 AI 已完成”识别其成果，也不会在用户没有再发消息或设置自动任务时持续后台等待。

## 交付与状态管理

任务状态使用“待决策、待开始、进行中、待整合、需修复、已合并、取消”。实现者完成代码只能报告“待整合”；整合者根据实际合并与验收证据标为“已合并”。整批验收单独记录，不能从某个任务完成自动推导。

实现者更新自己的任务卡与涉及的局部说明。全局技术状态、决策日志和批次总表由规划整合者统一维护，避免并行冲突。最终报告需包括完整 HEAD、PR、工作树绝对路径、变更范围、测试命令/结果、未测试项、遗留问题及未提交文件；不附用户秘密。

完成的批次材料留在原路径以便追溯，在 [工作台账](../../work/README.md) 从活动区转入已结束区。长期有效规则提炼进 current；任务记录不成为未来所有 AI 的默认必读资料。
