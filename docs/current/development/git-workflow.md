# Git 工作流与工作树整合

状态：依据用户授权选用并落实的工程协作规则。更新日期：2026 年 10 月 26 日。

阅读时机：创建任务分支、启动 Codex 工作树、提交、创建 PR、整合一批成果或清理工作树之前。角色与派工见 [AI 协作](ai-collaboration.md)，任务材料见 [工作台账](../../work/README.md)。

## 采用 GitHub Flow

Recorder 采用 GitHub Flow：从主分支建立短期分支，提交改动，创建 Pull Request（PR），审查验证后合并，再结束任务分支。它适合当前个人负责产品、多 AI 分工、持续增量开发的阶段；无需维护长期 `develop` 或提前建立发布分支。[GitHub 官方说明](https://docs.github.com/en/get-started/using-github/github-flow)

Conventional Commits 继续约束提交消息；它与分支工作流分别解决不同问题。下列分支前缀、压缩合并方式和任务编号是 Recorder 的配套约定，不是 GitHub Flow 强制规定。

## 分支、PR 与版本

| 分支 | 责任人与用途 | 生命周期 |
| --- | --- | --- |
| `main` | 规划整合者维护；当前可验证的共同基线 | 长期保留，通过 PR 更新 |
| `feat/<task-id>-<topic>` | 实现者；新增功能 | 一项任务完成后结束 |
| `fix/<task-id>-<topic>` | 实现者；修复问题，包括紧急修复 | 同上，不另设长期 hotfix 分支 |
| `docs/<topic>` | 规划者或获分配的实现者；规划、设计、文档 | 同上 |
| `chore/<topic>`、`test/<topic>`、`refactor/<topic>`、`ci/<topic>` | 工具、验证、重构和持续集成工作 | 同上 |
| `integration/<batch-id>` | 整合者独占；仅在批次必须整体落地时使用 | 临时分支，不替代 `main` |

使用简短的小写英文与连字符，例如 `feat/b001-t02-record-editor`。分支按任务划分，不按 AI 名字长期保留。Codex 已建立 `codex/...` 分支时可沿用，在任务卡登记完整名称即可；不要为了格式改写已有工作。

默认每个任务的 PR 指向 `main`，采用 **Squash and merge**：一个可独立验收的任务在主分支形成一个 Conventional Commit，原始提交仍可通过 PR 追溯。PR 标题使用 `feat(records): ...`、`fix(auth): ...`、`docs(workflow): ...` 等格式；不把多项无关需求堆进一个 PR。破坏兼容时使用 `!` 或 `BREAKING CHANGE:`，同时说明迁移方式。[提交规范](https://www.conventionalcommits.org/en/v1.0.0/)

批次若需要整体合并，必须在派工前明确：各任务 PR 指向该批次 `integration/...`，逐项审查并压缩合并；整合者完成联合验证后，再将该分支通过一个 PR 压缩合并到 `main`。台账记录子 PR 与最终批次 PR；不能把同一任务再合入 `main` 一次。未选择此模式的批次，按默认方式逐项进入 `main`。

目前不建立长期 `develop`、`release/*`，不创建空的未来任务分支。发布标签以后按实际发布使用 `vX.Y.Z`，早期可用预发布后缀；提交规范不等于每次合并都自动发布或升级版本。

## 主分支与仓库设置

下列设置已于 2026 年 10 月 25 日通过 GitHub API 启用并核对；以后调整或排查时仍需查询实际状态，不能仅凭本文认定设置未变。

- `main` 要求 PR，禁止强制推送和删除，要求线性历史，管理员也遵守。
- 仓库只开启 squash 合并，默认取 PR 标题作为最终提交标题。
- GitHub 必需审批人数暂设为 0：目前多个 AI 使用同一个用户账号，无法形成独立账号审批。整合者仍必须检查代码、测试和验收项，记录证据；这不等同于独立人员审查。
- PR 讨论须解决。已在 T02 成功运行后启用必需检查 `Quality (Windows)`、`Quality (Linux)`、`PR title`，来源限定 GitHub Actions（app ID 15368），且要求任务分支跟上目标分支。操作说明见 [CI 指南](../../../.github/CI.md)，实际证据见 [B001 台账](../../work/b001-record-editing/README.md)。
- 不自动删除远端任务分支；整合者确认交付映射、无后续依赖和工作树保留情况后再清理，防止提前失去任务定位信息。

本地 `commit-msg` 钩子仅检查提交标题，需执行 `git config core.hooksPath .githooks`；它不是服务端保护，也不能阻止他人绕过检查。若规范与线上设置发生漂移，先查明原因并报告，不悄悄放宽保护来合并。[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [Squash 设置](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests)

## 一个工作树对应一项在做的任务

工作树是独立文件目录；分支是提交历史的名称。工作树共享 Git 对象和分支引用，但拥有各自的工作目录与索引；它们不会自动合并修改。同一分支不能同时被多个普通工作树检出。各实现 AI 只在自己的目录、任务分支中工作。[Git worktree](https://git-scm.com/docs/git-worktree)

Codex 管理的工作树可能从 detached HEAD 开始。实现者应先检查 `git status`、`git branch --show-current`、`git rev-parse HEAD`，在当前提交上建立任务分支并记录起点，不强制切换到另一分支覆盖已有内容。以实际工作树状态为准，不假定未提交修改、依赖或忽略文件已随工作树准备完毕。[Codex 工作树文档](https://learn.chatgpt.com/docs/environments/git-worktrees)

每张任务卡记录基线的完整提交 SHA、实际起点、任务分支、PR 和工作树路径。新任务从已同步并核验的 `main` 开始；本地目录有用户修改时，先保留并辨明范围，不自动 stash、reset 或清理。

同一会话和工作树可以顺序处理多个任务；一项任务一条短期分支，不要求每项任务新建目录或会话。主仓库更新 main 只更新共享引用，不会把改动自动合入其他工作树当前检出的任务分支。前项已合并且成果保全后，在原工作树 `git fetch origin`，核对修改，再用 `git switch --no-track -c <新任务分支> origin/main` 建立新基线；无需检出被主仓库占用的 main。已有同名分支时先核对归属，不强制重建。切换后重新阅读最新指导、技术状态和任务卡，不能只依靠会话中的旧上下文。

各工作树自行安装锁定依赖。运行实例必须隔离端口、数据库目录、Electron 测试配置和临时文件；不能让多个 AI 共用真实 `.recorder/` 或用户桌面资料。业务测试优先使用项目已有的隔离测试脚本；不要把凭据和用户数据复制进新工作树。

## 依赖与同步

- 公共接口、根依赖/锁文件、迁移清单和全局文档在每批中分别指定唯一负责人。其他实现者提出变更需求，不同时编辑同一份公共文件。
- 依赖任务先合并；下游再以实际合并后的提交为基线。可以并行的任务，应具有相互独立的修改范围和已明确的接口约定。
- 若任务开始后 `main` 有变化，整合者安排分支所有者更新。默认将最新目标分支合入任务分支，不对其他 AI 的分支强推；这种同步提交也使用 `chore(sync): ...` 标题。
- squash 会产生新提交。不要把仍基于另一任务原始提交的旧分支直接继续提交 PR；先核对差异，必要时将该任务独有提交迁移到新分支并重新测试。不能只凭提交 SHA 不同认定改动未合并。
- `cherry-pick` 仅用于明确选取某段独立提交的恢复或迁移，须记录来源和新 SHA；不作为每批整合的默认操作，也不重复 merge 与 cherry-pick 同一改动。

## 整合者的实际流程

1. **接收交付。** 收集任务卡、分支、完整 HEAD、工作树路径、PR、测试结果与未完成项。要求任务改动已提交；存在未提交成果时先补齐交付，不能靠复制目录整合。
2. **检查基线。** 获取远端状态，核对目标分支、提交范围、已合并 PR 与工作树状态；记录本轮验证所针对的目标 SHA 和任务 HEAD。
3. **检查内容。** 审查实际 diff、验收标准、插件边界、接口/迁移兼容、数据保留、凭据及文档。AI 的“完成”陈述不是验证证据。
4. **按依赖顺序准备合并。** 必要时在整合者自己的临时分支/工作树预演合并。不修改其他仍在运行的工作树。公共接口冲突由整合者统一处理；涉及产品含义、数据丢弃或新架构选择时请用户决定，不能单凭 Git 无冲突就合并。
5. **验证合并结果。** 文档仅查修改及受影响内容、所属索引、必要引用、状态和编码，不再例行全量验证；可用 `pnpm check:docs --base <审查基线>` 或在命令后指定文件路径，并运行 `git diff --check`。无参数按 Git 变更选择，规则见 [CI 指南](../../../.github/CI.md)。代码变更根据范围运行构建、类型检查和相关测试；`pnpm check` 中的文档步骤也按相关范围执行。影响 Electron/账号记录流程时增加相应 smoke。Android 真机仍按用户要求延后，明确未执行范围。
6. **通过 PR 合并。** 检查远端 PR 的 HEAD 与已审查版本一致、目标没有新增未经验证的变化；变化后重新评估并补测。使用正常 squash 合并，不以管理员绕过失败条件。按顺序处理多个 PR，并对组合结果验收。
7. **更新台账。** 记录任务原 HEAD、最终主分支提交、PR、检查结果和遗留事项；同步当前技术状态、受影响的架构/运行说明，让用户获得一份整合报告。
8. **保留与清理。** 确认主分支和远端包含预期成果，保留需要的测试证据；计划复用的会话和工作树继续保留，仅在不再需要时清理。新的任务基于最新主分支建立新任务分支，不沿用已 squash 的任务分支。

预演成功不等于 PR 已合并；PR 合并不等于产品已发布。若 GitHub 无法访问，可完成本地审查和验证，保留任务分支，恢复访问后再完成 PR 流程。

## 失败、回退与工作树归档

冲突解决后必须复验受影响功能。集成失败只保留为待修复状态，不能通过删测试、覆盖一方代码或改写公共历史标记完成。需要回退已合并代码时，通常建立修复分支，通过 PR revert 相应 squash 提交；数据库已经迁移或写入新数据时，Git 回退不是数据恢复，必须另外评估兼容与恢复方案。

Codex 托管工作树优先用应用提供的归档/恢复功能，不手工强制删除托管目录。归档是环境清理，不会替代合并；需要保留的忽略文件先单独保存。本会话未必能直接归档其他会话拥有的工作树，届时由对应会话/用户完成；即使 Git 能读取其提交，也不能绕过应用归属。不能在未保全成果前强制删除分支或工作树。[Codex 工作树管理](https://learn.chatgpt.com/docs/environments/git-worktrees)
