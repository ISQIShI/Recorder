# Recorder 开发启动评估

状态：开工评估持续用于后续工作；基础工程已按用户授权实现，完整业务范围与排期未冻结。更新日期：2026 年 10 月 31 日。

阅读时机：判断能否开始开发、选择下一项设计工作、准备初始化工程或安排实现顺序时。先读 [技术状态](../technical-status.md) 和 [目录规划](repository-layout.md)；详细需求见 [当前需求](../product/requirements.md)。不加入所有日常任务的必读清单。

## 1. 结论与实际阶段

**现有设计足以开始工程搭建、关键技术验证和第一条业务流程开发；尚不足以将所有提案视为冻结规范，或宣称可以直接用于保存唯一一份重要资料。** 不需要先把全部功能和未来插件细节设计完，接下来应通过可运行结果消除不确定性。

用户已确认 TypeScript + Node.js、全面插件化并授权工程实现。基础工程后又完成账号初始化/登录、会话撤销和纯文本/Markdown 保存查询，见 [当前业务流程](first-record-flow.md)。初始迁移已实现，编辑、桌面回收站、标签与分层分类已完成，已有记录附件已由 B005-T01 实现，文件直接建记录与完整升级恢复仍待实现；新部署方向见 [本地宿主与同步](../architecture/local-runtime-sync.md)。

## 2. 已经足够明确的部分

| 方面 | 已有依据 | 对开工的意义 |
| --- | --- | --- |
| 产品与数据归属 | 个人资料与事务管理、可部署后端、三端入口、文件托管、多标签/分类、回收站 | 当前从单实例流程推进；未来 Android 本地宿主与同步另行验证，不再限定必须由 PC/服务器承载 |
| 技术主线 | Harness 维护版 Cordis/Loader、Fastify、SQLite/better-sqlite3、Drizzle；Electron、Vue/Vite、Capacitor | 可以围绕已选组合验证工程，不必继续横向比较同类框架 |
| 端间边界 | 业务和持久化在后端；共享 UI 经平台适配接入；统一 API/认证主线 | 可以定义并验证一条真实调用链 |
| 扩展与存储 | 核心记录 + 插件表、统一迁移账本、卸载默认保留 | 可以用一个小型业务插件验证边界，无需先设计插件市场 |
| 备份恢复 | 统一恢复集合 + 后台复制、本地与加密异地副本、restic | 可以设计故障与恢复验收，不从零自研备份引擎 |
| 文档协作 | current/design/history、AGENTS、各工程 README | 已能区分决定、提案与实施事实，适合 AI 按任务增量开发 |

判断来自对 [后端技术](../architecture/backend-stack.md)、[共享前端](../architecture/frontend-stack.md)、[Android 方向](../architecture/android-stack.md)、[数据访问主线](../storage/data-access-baseline.md)、[备份主线](../storage/backup-baseline.md) 及相应设计的审阅。各技术方向已经确定，不等于其版本组合经过验证。

## 3. 需要在什么时间补齐

| 时点 | 尚需明确或落实 | 建议处理方式 |
| --- | --- | --- |
| 基础工程（已完成） | TypeScript/Node 已确认；运行时、起步依赖、pnpm workspace、构建和 Git 已建立 | 具体版本和可逆工具配置由 AI 核验并记录，后续升级时复验，不要求用户逐个挑补丁版本 |
| 第一条业务流程（已实现子集） | 纯文本/Markdown、首次设置账号密码和记住登录已确认；账号与保存/查询已实现 | 编辑、桌面回收站、标签与分类筛选已实现；附件后续增量落实；未冻结完整 MVP，也不限制未来正文格式 |
| 首个 schema 与公共 API 落地前 | ID、时间、owner、版本和外键约束；schema 来源、错误/分页、并发与幂等；基础登录和会话撤销 | 将本次要实现的最小子集写成当前契约并以样例验收，其余继续保留为提案；不先生成所有业务表 |
| 插件及 UI 扩展接口发布前 | 插件声明、迁移与服务就绪顺序、在途操作处置；UI 贡献格式与设备能力适配 | 用一个含数据、公开操作和 UI 入口的小插件检验；随客户端分发 UI 与独立热安装仍需区分，不能凭后端热加载推导三端动态安装 |
| 首次真实使用前 | 数据目录、文件提交/清理恢复、会话和密钥保存、备份与实际恢复、可定位的错误与日志 | 用隔离样本完成崩溃、重试和恢复验证，再导入真实资料；目标是可恢复且不误报保存成功 |
| 提供安装包或跨设备部署前 | Windows 是否附带后端及其生命周期；首用初始化、HTTPS/连接设置、升级与卸载、Linux 运行配置 | 根据用户先使用 PC 还是服务器确定分发体验；网络部署可以晚于本机联调，不能晚于真实远程接入 |
| 实现相应业务模块时 | 日程重复与时区、提醒误差与计划范围、金额/币种、Android 暂存容量/取消、中文检索等 | 每次落实一个模块的行为与验收，不要求这些问题全部回答才开始基础工程 |

已有提案覆盖了这些问题的大部分方向，缺口主要是**尚未确定具体契约和缺少验证**，不是完全没有设计。接口和身份见 [统一 API](../../design/interfaces/unified-api.md)、[认证设计](../../design/security/identity-device-access.md)，模型和文件见 [数据模型](../../design/storage/data-model.md)、[存储生命周期](../../design/storage/storage-lifecycle.md)。

## 4. 应尽早验证的技术风险

| 验证项 | 为什么应早做 | 能支持继续开发的证据 |
| --- | --- | --- |
| Cordis 独立宿主与配套 Loader | 源码说明/公开包存在不等于 Recorder 组合可运行 | 锁定依赖后实际启动，插件启停和依赖消失/恢复不重复注册或泄漏资源；维护与迁移不依赖业务插件先启动 |
| SQLite、Drizzle 与迁移适配 | 账本和业务表需要同事务成功事实，文件无法依赖数据库回滚 | 核心和示例插件建库、升级、失败回滚/重启对账；保留已卸载插件数据，拒绝不兼容升级 |
| 附件提交与备份一致性 | 数据库成功、文件落盘和后台复制是不同边界 | 中途退出后不产生被当作正常记录的缺失附件；备份期间替换/删除对象，仍能恢复完整集合 |
| 三端契约与 UI 扩展 | 共享 Vue 不等于所有设备能力或凭据可以共用实现 | Web 与 Electron 用同一契约读写；平台桥接不泄漏凭据；插件能力变化后 UI 有明确状态；Android 验证同一接口可接入 |
| Android 分享、暂存及通知 | URI、进程回收、权限和系统调度必须真机验证 | 分享后进程退出仍能找回待提交内容；回包丢失不重复建记录；已有提醒在目标条件下触发，失败和受限状态可见 |
| restic 与跨平台恢复 | 命令成功不等于业务数据可恢复 | 本地/异地分别核验，读取和隔离恢复后检查数据库、附件与插件数据；在目标 Windows/Linux 环境验证工具与权限 |

插件验证遵循所选维护版的生命周期机制，不再创建第二个加载框架。[Harness 生命周期说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-tutorial/02-lifecycle-and-effects.md) 说明框架行为，不证明 Recorder 的后台任务或持久数据已正确恢复。

相关验证场景已经在 [迁移提案](../../design/storage/plugin-migrations.md)、[备份恢复](../../design/storage/backup-recovery.md)、[restic 集成](../../design/storage/restic-integration.md)、[Electron 协作](../../design/architecture/backend-electron-boundaries.md) 和 [Android 协作](../../design/architecture/backend-android-boundaries.md) 中列出。应随相关功能实现执行，不把全部测试当作初始化前的先决条件。

## 5. 建议的启动顺序

1. **建立可重复启动的工程。** 确定运行时和工具链，建立 Git、依赖锁定、必要检查；验证 Cordis/Loader、Fastify、数据库、共享契约及 Vue 能一起运行。先不搭建大量没有使用者的公共抽象。
2. **逐步扩展真实流程。** 保存/查询、[B001 编辑](../../work/b001-record-editing/README.md) 及 [B002 维护与隔离恢复](../../work/b002-migration-recovery/README.md) 已完成范围内验收。按用户 2026 年 10 月 28 日的核心优先要求，[B003](../../work/b003-record-management/README.md) 先补桌面回收站和标签筛选，再建议接分类与基础附件；使用现有维护 CLI 升级，不以桌面维护 UI 为前置。T01 回收站和 T02 标签与筛选均已验收，本批结束；[B004 分层分类](../../work/b004-record-categories/README.md) 已通过 PR #18 验收，完成查询含后代去重、删除整棵分类树保留记录等桌面流程。当前已定稿 [B005 基础附件](../../work/b005-managed-attachments/README.md)：先 T01 已有记录附件及必要恢复兼容，再 T02 文件直接建记录；用户已确认收集方式、永久删除语义与至少 1 GB。T01 已通过 PR #20 验收，T02 待启动；原生对话框已补验，日常备份及正式恢复启用仍后置。
3. **按桌面优先完善扩展与设备能力。** 用户已确认先推进 Windows，Web/Android 后续依据桌面实施与工作记录补齐，具体见 [交付顺序](../architecture/frontend-stack.md)。继续保持共享契约与现有构建检查；Android 分享、持久待提交及提醒的真机风险尚未验证，后续进入该端任务时再安排，不作为当前批次的必经前置。
4. **随核心功能做必要验证。** 复用已有迁移、恢复与 CI 成果，覆盖新增主流程、数据归属及必要并发行为，不把完整备份、更多故障防御或增强工具当作每项核心功能的前置。日程、待办、订阅和统计按实际使用需求进一步选择。

上述第一步的基础部分已完成，验证未覆盖所有风险；其余仍是建议顺序，不是完整 MVP 或排期。质量检查围绕真实行为：类型/构建、关键事务和契约测试、跨端流程及故障恢复；不因文档列出候选命令就宣称可以运行。

## 6. 可以继续保留弹性的事项

AI 模型与整理流程、第三方插件市场、复杂动态 UI 安装、桌面临时中转、跨后端同步、所有文件格式的预览与编辑，都不阻碍当前基础工程。它们被推迟细化不代表删除既有需求；公共边界足够承接后续扩展即可，不能预先承诺所有未知插件无需客户端升级。

异地服务商、长期保留天数和具体资料规模可以在接入实际目标前决定；但首次备份发布前必须明确恢复凭据、保护规则和成功标准。性能先记录参考设备、数据规模、启动/唤起、查询及上传耗时，再与用户确定体验目标，不虚构达标数字。

## 7. 工作状态维护

用户的启动授权已经生效。每次只将已确认并准备实现的契约子集从 design 提炼到 current；完成后补充真实脚本、测试证据和未解决限制。用户决定产品体验及会改变方向的选择，AI 承担版本核验、常规工程细节和验证工作。

当前已开始工程实现，仍未执行性能测试或完整恢复演练；工程验证通过不等于可以正式上线或保存唯一一份重要资料。Android SDK 配置按用户安排延后，指引见 [环境配置](android-environment.md)。
