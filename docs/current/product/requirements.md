# Recorder 当前需求

状态：已确认需求与开放问题。更新日期：2026 年 10 月 29 日。

Recorder 是一个由可部署后端提供业务能力的个人资料与事务管理工具。当前后端面向 PC/服务器，未来也考虑 Android 等设备本地处理和网盘等云同步，不强制 PC 或服务器常驻，详见 [本地宿主与同步](../architecture/local-runtime-sync.md)。它面向工作与生活中的文本、文件、音频、视频及其他数据，支持临时收集和长期保存，并逐步提供组织、检索、提醒、统计和 AI 整理能力。

项目名称继续使用 **Recorder**。本文件记录用户已明确的目标与仍待讨论的问题；Windows、Android、共享界面与后端技术主线已选定，具体实现继续讨论，目前不划定 MVP 或开发排期。阅读时机：需求设计、功能验收和范围调整。导航见 [当前文档索引](../README.md)，当前架构见 [后端与客户端职责](../architecture/overview.md)。

## 已确认的使用范围

2026 年 10 月 28 日优先级更新：用户要求先完成、完善主要核心功能，增强及附加功能降级。规划者据此安排 [B003 回收站与标签筛选](../../work/b003-record-management/README.md)，先补日常记录管理；回收站及标签筛选均已通过 B003 验收，Windows 桌面完整流程可用；Web/Android 新增流程尚未独立验收。B004 分层分类已通过后端到桌面验收，当前按 [B005 基础附件计划](../../work/b005-managed-attachments/README.md) 顺序推进已有记录附件与文件直接建记录，再按反馈扩展事务能力，不冻结完整排期。桌面维护 UI、恢复增强、备份自动化、AI、同步、多端补齐和复杂编辑器暂不阻塞核心功能交付，原需求仍保留。

| 场景 | 用户希望覆盖的内容 |
| --- | --- |
| 日程和待办 | 安排事项、跟进任务，支持提醒和重复安排 |
| 工作和生活 | 保存日常信息、工作资料和生活记录 |
| 会议 | 收集会议相关文本、文件、音频和视频 |
| 开销 | 记录支出，并支持统计 |
| 订阅和续费 | 管理会员、订阅制服务及其他定期续费项目 |
| 通用资料 | 临时或长期保存任意形态的数据，不将工具局限于某一种笔记格式 |
| 桌面临时中转 | 便捷存取刚复制的文本、刚截的图、刚录的视频及临时文件；可通过后期插件扩展 |

用户已经确认：除了保存和检索，还希望工具能主动提醒、处理重复安排并提供统计。Android 日程与续费提醒希望尽量准点，短时断网或 PC 后端关机时也希望已有提醒继续触发。具体误差标准、系统条件、提前登记范围、业务规则及统计口径仍需细化。

## 数据与文件

- 数据保存在当前业务后端所在设备；支持未来各端本地处理，逐步提供新增、删除、修改和查询。
- 支持文本、文件、音频、视频等形态，兼顾临时内容和长期资料。
- 文件默认复制到后端管理的资料库；文件来自另一台客户端设备时，需要传输到后端。保留只关联原文件的需求，但其适用范围需按文件位置明确。
- 首版附件已确认：可选择文件直接新建无正文记录，也可给已有记录添加附件；单文件至少支持 1 GB，音频/视频先按普通文件保存和取回。B005 工程验收采用 1 GiB（1,073,741,824 字节），当前仅规划。
- 单独移除附件须明确确认后永久删除，本批不跨记录共享附件；原始文件保留。此操作不等于删除整条记录，记录回收/恢复继续保留附件，确认清空时再清理。
- 一条记录支持多个标签，并可同时归入多个分类；分类可以分层。已按 [B004 任务卡](../../work/b004-record-categories/README.md) 实现并验收桌面分类树管理、多分类归属与筛选；用户已确认查询默认包含全部子分类并去重，明确确认后可删除整棵分类树；所有正常/回收站记录、标签与树外分类归属保留。Web/Android 分类流程尚未独立验收。
- 删除记录先进入回收站，需要时可恢复；清空时再确认彻底删除。尚未指定自动清空、保留期限或磁盘擦除规则。
- 当前先完成单实例保存与查询；未来支持各端本地处理并经网盘等云存储同步。共享同一后端和多实例同步是两种模式，具体同步协议待设计。
- 第一条记录流程已确认同时支持纯文本与 Markdown，并明确保存正文格式；账号首次设用户名密码，之后可记住登录及撤销会话。
- 编辑已有记录采用手动保存；离开有未保存修改的界面前提醒。版本冲突时保留草稿，让用户决定如何处理，不默认自动合并或强制覆盖。具体待实现行为见 [编辑契约](../interfaces/record-editing.md)。

“可以保存任意文件”与“能够预览、编辑、转写或理解每种格式”需要分别定义。后者可按格式逐步扩展，当前没有承诺内置所有格式的编辑器。

数据组织主线已确认采用统一记录基础、独立附件、标签分类关联和插件业务表，工作依据见 [数据模型主线](../storage/data-model-baseline.md)；具体字段、编辑格式和迁移机制继续设计。查询及迁移工具已另行确认，见 [数据访问主线](../storage/data-access-baseline.md)。

关联原文件时，文件仍由原位置管理。后端可访问的文件与仅存在于客户端的文件需要区分：向远程后端提交客户端路径，不会使文件内容自动变得可访问。跨设备关联、文件移动或删除后的处理方式尚待确定。默认托管文件与外部关联文件需要让用户能够区分。

## 平台与部署

交付顺序已于 2026 年 10 月 26 日明确：先完善 Windows 桌面端，Web/Android 不必同步推进新增功能；待桌面功能相对完善，再依据桌面实施与工作文档补齐其他端。保留公共契约、共享界面边界和现有构建检查，不取消其他端需求。具体工作规则见 [前端技术](../architecture/frontend-stack.md)。

优先考虑的平台为 Windows、Web 和 Android。Windows 使用 **Electron**，共享界面使用 **Vue 3 + TypeScript + Vite**；Android 使用 **Capacitor + Vue，必要时用 Kotlin 补充原生能力**。起步版本与实际结果见 [工程基线](../development/engineering-baseline.md)，选型范围见 [前端技术](../architecture/frontend-stack.md) 和 [Android 方向](../architecture/android-stack.md)。保留未来接入其他桌面或移动客户端的空间。

用户提供的常用 Android 设备为“荣耀 Magic9 超能版”，并说明能正常使用 Google Play 服务。这是设备环境信息；系统具体版本、通知权限和实际推送到达情况尚未验证，不由此自动确认 FCM 或其他通知方案。

当前后端以 Node.js 面向 Windows/Linux，例如本机或云服务器。未来可由 Android 等设备承载本地业务后端；前端与业务层保持插件化职责分离，并不要求它们始终在不同设备。

用户已确认同一台后端先只供自己使用，同时保留未来增加账号的空间。当前不要求多人共享编辑、组织或团队管理。API 已选 HTTP/REST + OpenAPI + SSE，认证已选本地账号与后端可撤销会话，范围见 [API 与认证主线](../architecture/api-auth-baseline.md)；具体登录交互、设备授权与凭据实现继续设计。

前端负责界面展示和交互，业务规则、增删改查、分类整理、统计及持久化由所连接的后端承担。当前实现先使用 PC 上的 Node 后端；后续用户已扩展为允许 Android 等设备承载本地后端和同步，不继续用早期集中部署限制否定该方向，具体宿主和同步机制仍待验证。

后端部署在本机且可运行时，同机客户端不依赖互联网即可访问；连接远程后端的客户端需要能够访问该后端。用户已确认 Android 快速收集和分享场景在后端不可达时先暂存到手机，连通后自动重试，并明确显示尚未保存到后端。这是提交前暂存，不是独立完成业务操作；Windows/Web 的暂存，以及其他业务操作能否离线排队尚未确认。

## 快速唤起与输入

希望随时快速收集信息，已提出的入口包括全局快捷键、系统托盘和剪贴板监听。

这些是使用目标，具体入口需根据平台能力设计。Windows 优先考虑桌面系统集成；Android 和 Web 的入口需要分别讨论，不能直接承诺与 Windows 拥有相同的后台监听能力。

## 桌面临时中转空间

希望 Recorder 能承担桌面端临时存放和取用资料的功能，覆盖复制内容、截图、录制视频及临时文件等场景。该能力可作为后期插件扩展，当前不作为核心功能。

用户已选择以主动放入为主：通过快捷键收集当前剪贴板、拖入文件或粘贴内容。使用体验应便捷，减少为了临时存放而填写分类、标题等信息的负担。仅推进该功能时阅读 [桌面临时中转设计](../../design/product/temporary-shelf.md)。

## 插件架构

插件卸载默认保留数据，移除代码不等于删除其资料；重新安装、导出及单独清除的具体交互继续设计。迁移已选 Recorder 统一命名空间账本与受控 SQL 执行适配，确认范围见 [数据访问主线](../storage/data-access-baseline.md)。

用户明确选择：采用 DeepSeek Harness 所使用的 Cordis 技术体系，沿用它的插件机制构建独立的 Recorder 产品。无需将 Recorder 定义为 Harness 的一个业务插件，也不自行重写一套外观相似的插件框架。

用户进一步明确“一切皆插件”：前端、后端以及其中的功能模块均通过插件实现，达到可替换、可插拔的目标。HTTP、数据库、认证、迁移、备份、UI、客户端连接、设备入口和 AI 等均纳入要求；具体服务契约与验证边界见 [全面插件化](../architecture/plugin-everything.md)。不再把前端或基础能力是否插件化作为可选方向。

插件最初主要服务个人扩展，未来可能允许第三方开发。当前没有确认插件市场、跨平台插件完全通用或现有 Harness 插件直接兼容。

用户已进一步确认使用 Harness 维护版 `@deepseek-ai/cordis` 及配套 Loader，同时选定 Fastify、SQLite + better-sqlite3，后端语言与运行时为 TypeScript + Node.js。工程基线在实现中锁定，当前依据见 [已确认后端技术](../architecture/backend-stack.md)。此选择不要求复用 Harness 的完整应用或 React 前端。

## AI 与对外开放

AI 优先用于自动分类、整理和归纳。后端需要保留供客户端、自动化工具及未来 AI 调用的能力。

AI 使用本地模型还是云端服务、哪些资料可以发送到外部、分类结果是否直接生效、能否修改或删除原始资料，均未确定。自然语言操作、语义检索、音视频转写等可继续讨论，目前不视为已确认需求。

## 开发与维护方式

已有资料库需要结构升级时，先说明需要升级，由用户点击确认后执行；升级暂停业务写入，并先创建恢复点，优先保证数据完整与恢复可靠。普通启动不自动升级已有库。当前实施子集见 [迁移恢复契约](../storage/migration-recovery-contract.md)，完整维护与恢复见 [迁移机制提案](../../design/storage/plugin-migrations.md)；维护 UI 尚未实现。

日常备份与结构升级分别对待：备份期间尽量保持可用，只接受很短的快照窗口；已选“统一恢复集合 + 后台复制”，副本采用“本地独立副本 + 加密异地副本”，工具已选 restic，确认范围见 [备份恢复主线](../storage/backup-baseline.md)。具体版本、保存位置、频率、保留期限、密钥保存与恢复耗时目标未定，执行细节见 [备份恢复提案](../../design/storage/backup-recovery.md)。

主要由 AI 完成开发，用户负责需求表达、方向选择和验收。用户已授权工程搭建和关键验证；起步版本已经锁定，具体功能与配套按需细化。技术选择应考虑用户长期理解、诊断和维护项目的成本。

用户允许根据前后端分离、多前端的需要，在根目录建立独立工程目录。本轮已建立后端、桌面、Web、Android 与共享区域的说明入口，详见 [工程目录规划](../development/repository-layout.md)；未初始化应用或锁定包管理器。

用户明确将即时唤起与响应性能、可维护性、可扩展性放在同一优先级，资源占用低一个优先级。尚未指定内存、CPU 或唤起耗时的硬指标；不能为了降低常驻占用而默认牺牲快速可用的体验。

## 后续需要细化的问题

| 问题 | 为什么影响设计 |
| --- | --- |
| 后续 Markdown 预览、富文本等编辑器如何扩展 | 当前已确认纯文本 + Markdown，后续保持版本化格式；见 [模型细化设计](../../design/storage/data-model.md) |
| 附件复用和文件清理行为 | 分类查询/删除已确认并纳入 B004；附件复用、解除关联及物理文件清理规则仍需细化 |
| 备份具体目的地、周期、保留期限、可接受数据损失与恢复耗时；是否需要编辑历史 | 统一恢复集合 + 后台复制、副本方向和日常备份可用性已确认，详细方案见 [备份恢复](../../design/storage/backup-recovery.md)；备份与编辑历史、回收站分别设计 |
| PC 后端是否需要供外出时的 Android 访问 | 影响局域网、私有网络与公网入口的选择；见 [部署接入提案](../../design/operations/deployment-access.md) |
| 首次登录与加设备的便利性、凭据恢复和会话保留期限 | 使用主体已确认；影响具体认证流程，不要求现在建设完整多用户产品 |
| 尽量准点的具体误差、提前登记范围和受限时的提示 | Android 目标已确认；这些细节影响后端计划、系统定时与离线覆盖时间 |
| 重复安排如何处理月底、时区变化和错过的事项 | 决定日程、待办和订阅之间能共享哪些规则 |
| 临时资料如何取出、清理或转为长期资料 | 决定中转体验与生命周期，不能默认自动删除 |
| 单文件和总资料库大致多大 | 影响上传、大文件处理、附件下载和备份方式 |
| 只关联原文件是否限定为后端可访问的文件 | 影响远程部署时的可用性 |
| AI 可以访问哪些数据，整理结果如何撤销 | 影响 AI 的接口和操作边界 |
| Android 暂存的容量、保留、编辑与取消方式；其他端是否也暂存 | Android 收集暂存与自动重试已确认，其他行为仍需细化，不等同于独立业务处理 |
| 设备采集、UI 扩展与后端业务如何组合 | 已有 [Electron 协作提案](../../design/architecture/backend-electron-boundaries.md) 和 [Android 协作提案](../../design/architecture/backend-android-boundaries.md)，具体扩展契约仍需细化 |
| 多实例身份、网盘同步对象、加密和冲突处理怎样定义 | 本地处理和云同步方向已提出，具体协议和体验仍待设计 |

技术候选见 [当前技术状态](../technical-status.md)。需要追溯需求变化或论文依据时，再阅读 [决策与需求演进](../../history/decisions/decision-log.md)。
