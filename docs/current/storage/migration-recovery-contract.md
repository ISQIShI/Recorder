# 数据库升级与恢复演练契约

状态：B002 的实施依据；T01 计划、逐步执行与安全启动已实现，T02/T03 尚未实现。更新日期：2026 年 10 月 26 日。

阅读时机：实现或审查迁移计划、升级恢复点、维护入口和恢复演练时。先读 [数据访问主线](data-access-baseline.md)，任务入口见 [B002](../../work/b002-migration-recovery/README.md)。本页将本批需要的工程约定从 [完整迁移提案](../../design/storage/plugin-migrations.md) 提炼出来，其余提案仍未冻结。

## 用户决定与本批范围

用户已确认：已有资料库需要升级结构时，先说明需要升级，由用户点击确认后执行；升级暂停业务写入，先创建恢复点，优先保证数据完整和恢复可靠。普通启动不意味着用户同意升级。

规划者据此安排三项顺序任务：多版本迁移、独占与恢复点、维护入口与恢复演练。当前后端独立运行，本批先实现由本机操作系统权限保护的离线维护 CLI；用户显式执行并确认升级计划是该工程入口的授权。桌面的说明与确认按钮仍是后续必须实现的产品交互，本批 CLI 不代表已经兑现桌面体验，也不冻结远程管理 API。

本批仅覆盖当前一份 SQLite 中的账号、会话、记录及插件业务表。附件、插件外置文件、日常备份、restic 仓库、跨设备同步、在线停写切换和覆盖正在使用的资料库均不在本批。以后出现外部持久数据时，必须扩展恢复集合并验证一致性，不能继续把数据库快照称为完整资料库备份。

## 插件边界

| 能力 | 提供者职责 | 消费边界 |
| --- | --- | --- |
| 迁移计划与执行 | Cordis 迁移服务：检查安装清单、账本、摘要、依赖，生成只读计划，受控执行 | 业务插件提供可信的静态 SQL 与元数据，不各自启动迁移；不加载业务副作用才能读取迁移材料 |
| 资料库独占 | Cordis 存储宿主能力：在打开业务数据库前取得独占，所有数据库句柄关闭后释放 | 普通业务宿主和维护宿主使用同一规则，失败立即拒绝进入写入路径 |
| 恢复点 | Cordis 恢复点适配：数据库一致快照、清单、校验和封存 | 迁移协调者要求有效恢复点后才能升级已有库；不耦合未来 restic 子进程 |
| 维护协调 | Cordis 维护服务：预检、确认、恢复点、升级、验证和结果记录 | CLI 仅负责参数与确认交互、装配最小 Loader profile、呈现结果；以后桌面通过经认证的后端接口调用同一业务服务 |

服务类型放在后端契约文件，消费者依赖服务，不直接导入具体提供者。可复用的无副作用函数属于对应插件实现；不能在 `main.ts`、CLI 或另一个单例控制器里再写一套迁移业务。服务撤回、失败、dispose 时释放资源；不能将持久 SQL 效果当作可随插件 dispose 撤销的运行时效果。

这是可信已安装代码的协调边界，不是针对恶意第三方 SQL/Node 插件的安全沙箱。第三方代码隔离另行设计。

## 版本、账本与只读计划

1. 保留实际已有的 `recorder_migrations(namespace, revision, digest, applied_at)` 成功账本以及 identity/records revision 1 的 SQL 原字节和摘要算法。不重建库、不改已应用 SQL、不引入每个插件独立的 Drizzle 权威账本。
2. 每个命名空间按连续正整数 revision 递增，当前已安装命名空间的迁移包保留完整历史；一项迁移以 `(namespace, revision)` 唯一定位。软件包版本与数据 revision 分别记录，不能互相推导。
3. 依赖精确到命名空间和最低数据 revision；同命名空间前一个 revision 是隐式前置。现有 `requires: string[]` 可兼容映射为所依赖命名空间 revision 1；新步骤使用明确版本的依赖。先校验重复、缺口、缺少依赖、循环、已有摘要和软件低于数据版本，再进行确定性的拓扑排序。
4. 没有提供者的历史命名空间及数据原样保留。若本次步骤依赖它，则必须有可验证的对应历史材料和满足版本的账本；不能把“插件已卸载”当作允许删表或跳过依赖的理由。
5. 预检输出状态（空库初始化 / 已兼容 / 需要升级 / 阻塞）、当前与目标 revision、顺序、原因和计划摘要。摘要绑定资料库定位、已应用账本及待执行 SQL/依赖元数据；执行前重新核对，不能复用过期确认执行新计划。
6. 预检不创建账本或业务表，不升级、不修复摘要。已有用户表却缺少可信账本、无法验证的历史、数据库损坏或版本不兼容时明确阻塞，保留数据。

全新空库的首次建表可沿用自动初始化；对已有库新增一个业务插件的数据表同样属于升级，需要确认与恢复点。非空库的判断不能只看文件大小或“没有记录”，也不能用无账本推定为空库。

## 启动与执行规则

普通业务启动只允许空库初始化或运行已经完全兼容且无未解决维护运行的库。发现待升级、不兼容或未完成维护时，不注册可写业务服务/路由，释放资源，以可识别的维护原因结束；本批不要求常驻维护 HTTP 服务。当前 CLI 或后续 UI 要能区分需要升级、版本不支持、库忙及损坏，不能全部显示为网络失败。即使全部迁移步骤已提交，也不能绕过尚未完成的整体验证与维护结束记录进入业务。

已有库的执行顺序为：

```text
取得资料库独占 → 只读预检 → 展示并确认同一计划
  → 创建并校验升级前恢复点 → 再核对计划
  → 按依赖逐步事务执行 → 整体验证 → 记录完成 → 关闭并释放
```

独占从预检持续到维护结束；业务进程仍占用库时，维护操作返回忙，不杀进程或强夺锁。多客户端继续连接同一个业务后端；这里限制的是多个独立后端同时打开同一个本地资料库，不是限制前端数量。

每步 SQL、外键验证和成功账本写入处于同一 SQLite 事务。失败时回滚本步，之前已提交的步骤保留；这不是整批自动回滚。默认停止，不继续启用业务、不自动降级、不自动覆盖恢复。SQLite 保证单个事务的原子性，并不保证整批应用协议或备份文件的一致性。[SQLite 事务说明](https://www.sqlite.org/transactional.html)

本批受控 SQL 限于已有 CREATE TABLE/INDEX，以及经审查的普通表 `ALTER TABLE ... ADD COLUMN` 子集，足以验证新增可空字段。使用驱动的单语句 prepare 边界，保留 Drizzle statement-breakpoint 支持。禁止脚本自行 BEGIN/COMMIT、ATTACH、PRAGMA、加载扩展、创建触发器、删除/重命名/重建表、修改账本或任意 DML；不引入完整 SQL 解析器。未来需要其他变换时单独扩展契约、审查数据语义及故障测试。本批不通过修改真实 identity/records schema 制造演示需求，使用隔离的多版本样本。

## 独占、恢复点与中断

独占必须能在 Windows/Linux 的独立进程间生效，基于规范化后的实际业务数据库路径，而不只是 `dataDir` 或进程内变量。覆盖显式 `filename`、相对路径、符号链接/Windows junction 等别名；不能可靠识别的别名应明确拒绝或限制支持，不能宣称任意路径安全。内存数据库只用于隔离测试。

实现者优先验证复用当前 SQLite 驱动持有独立控制库锁的方案；这是待验证的工程候选，不是已证实的算法。锁文件不能因旧时间戳自动删除，不能通过删除/替换锁文件绕过活跃持有者，控制文件不进入恢复切换目标。若改用新依赖或存在平台缺口，先报告证据与选择，不悄悄扩大依赖。只能协调遵守此规则的 Recorder 实例，不能阻止旧版本、数据库编辑器等绕过协议的程序；执行维护前须停止这些程序。网络文件系统不在本批支持范围。

恢复点在独占下通过 SQLite 一致快照接口生成，优先用当前驱动的 backup 能力；不复制仍在使用的 `.sqlite`/`-wal`/`-shm` 文件组合。[SQLite Backup API](https://www.sqlite.org/backup.html)

恢复目录由内部生成 ID 命名，先写临时状态，完整验证后才标为可用。清单至少保存格式版本、创建时间、计划摘要、成功账本、程序/依赖版本标识、SQL 材料和文件摘要、数据库文件及校验结果；保存必要的恢复说明。版本标识不等于已归档可执行程序，缺少旧版本程序时须明示恢复后能否启动，不能承诺任意版本自动运行。

数据库快照同时执行 `integrity_check` 与 `foreign_key_check`，验证已应用账本与清单一致；只核验文件 hash 或能打开 SQLite 都不够。前者不涵盖外键错误。[SQLite 校验说明](https://www.sqlite.org/pragma.html#pragma_integrity_check)

空间不足、复制失败、摘要不符、无法封存均禁止开始升级。未封存目录不列为有效恢复点。恢复点可能包含账号摘要和会话等敏感持久数据，放在受本机权限保护的独立目录，不提交仓库或输出正文/凭据到日志；本批不引入外传或自动清理保留策略。

维护运行记录与成功迁移账本职责分离：运行记录保存计划、恢复点、阶段及结果，成功账本是判断每一步是否提交的依据。原子更新/持久化运行记录，不把记录文件写成功等同于事务已提交。启动发现未完成运行时必须核对实际账本：保留“可继续 / 已提交但待最终验证 / 需人工处理”状态，不自动重试。继续前显示当前进度并再次显式确认；验证原恢复点、计划材料和账本前缀，无法对应则阻塞。

模拟中断至少覆盖快照未封存、步内未提交、步骤提交后结果记录未写、全部步骤提交但最终验证未完成。进程被终止的测试不等于已经验证真实断电、磁盘损坏或所有文件系统持久性。

## 维护入口与恢复演练

维护 CLI 分为只读检查、确认后升级、查询恢复点、恢复到隔离目标及验证。命令名称由实现者在 README 固定；交互执行展示计划并要求确认，非交互必须显式提供刚检查过的计划摘要作为确认，不提供隐含同意的默认参数。失败返回非零退出码和可识别原因，不泄漏资料或认证信息。

最小维护 profile 只加载独占、数据库访问、迁移、恢复点及维护协调插件，不依赖可能尚未升级的账号/记录业务插件，不开放 unauthenticated HTTP。正式桌面/远程维护需要另外设计可用的认证、授权与状态通道，不能为了在升级前能登录就绕过正常认证。

本批恢复只允许写入新建且为空的隔离目标，拒绝源目录、源库路径、恢复点目录及其相互覆盖的别名；禁止覆盖任何已有资料、替换在线库、自动启动业务服务和连接外部副作用。恢复后检验文件摘要、账本、完整性、外键，以及样本账号和记录的预期内容。恢复点不变，原资料库不变；若失败，目标保留明确未完成状态，不当作可运行库。

恢复后的正式启用、会话失效/重新认证、资料库身份、外部任务去重和桌面确认界面属于后续决策与实施范围。隔离演练通过不能写成“完整灾难恢复已完成”。

## 验收与事实边界

Windows 本机及 Linux CI 验证升级成功、拒绝/取消、恢复点失败、逐步回滚、中断重开、重复执行、跨进程独占、提供者替换/撤回，以及恢复到新目录的数据等价性。使用样本库，禁止对用户 `.recorder/` 做升级或恢复试验。

当前生产清单仍仅 identity/records revision 1。T01 已通过 PR #9 实现计划器、独立低层执行插件与普通启动门禁，隔离样本多版本迁移已验证，见 [任务交接](../../work/b002-migration-recovery/t01-versioned-migrations.md)。未完成维护运行门禁、独占、恢复点及维护 CLI/隔离恢复仍属 T02/T03；不能由 T01 的 compatible 状态推导整批维护完成。官方资料核对日期：2026 年 10 月 26 日；文件系统和驱动适配必须以本项目实测为准。
