# Recorder 业务插件数据扩展提案

状态：插件业务表、Recorder 统一命名空间账本与受控执行适配、卸载默认保留数据已确认；具体扩展契约、迁移 API 和插件 SDK 仍为建议。更新日期：2026 年 10 月 25 日；基础技术资料核对日期：2026 年 10 月 24 日。

阅读时机：业务插件需要保存字段、建立关系、参与查询、删除或升级迁移时。先读 [后端技术](../../current/architecture/backend-stack.md)、[数据模型](../storage/data-model.md)；网络公开能力见 [统一 API 设计](../interfaces/unified-api.md)。

## 1. 复用 Cordis，明确持久化责任

Cordis 及配套 Loader 继续管理依赖、启停和运行资源；Recorder 的数据契约规定表归属、事务、迁移及文件引用。不另造插件加载框架，也不把卸载作用域解释成数据库回滚或删除资料。

推荐核心提供账号上下文、记录、附件、标签分类、事务、迁移及持久任务服务。业务插件通过这些服务维护公共数据，并拥有自己命名空间下的业务表。核心公共服务也可由 Cordis 插件承载，“核心”描述稳定契约，不要求都硬编码在一个入口文件。

## 2. 什么放核心，什么放插件

| 数据 | 推荐归属 | 例子 |
| --- | --- | --- |
| 所有资料共用的身份与组织信息 | 记录和组织公共服务 | 用户、标题、正文、附件引用、标签分类、回收站状态 |
| 有业务含义且需要查询/约束的字段 | 插件自有关系表 | 待办状态、日程规则、订阅周期、支出币种与金额 |
| 少量、不常筛选的扩展属性 | 有命名空间和 schema 版本的 JSON | 导入来源的附加属性、插件展示配置 |
| 可重新计算的结果 | 明确标识的派生表/索引 | 搜索文本、缩略图状态、经确认可重建的统计缓存 |
| 执行状态 | 插件或公共作业服务 | 续费提醒投递、识别任务进度；不为每条投递创建资料记录 |

需要出现在统一资料列表、分类或检索中的业务对象，可关联一条核心 record。一个 record 可同时挂接多个插件能力；纯执行日志和业务内部明细不必全部伪装为 record。

举例：订阅记录的名称、说明、发票附件和分类由公共服务管理；周期、币种、金额、时区与续费规则由订阅插件管理。已发生的扣费和提醒投递可作为独立明细，不能只靠更新“下次续费日期”替代历史业务事实。具体业务模型后续按功能设计。

## 3. 推荐同库扩展表，JSON 有边界

推荐先在同一个 SQLite 数据库建立带稳定插件前缀的表，例如逻辑上的 p_subscription_*。插件标识由安装注册信息映射，不能直接把外部输入拼成 SQL 表名；核心表的列不因每个插件安装而改变。

同库便于公共记录与业务数据一起提交，统一备份与跨表约束。每插件独立数据库可以提供更强的物理分离，但会增加跨库一致性、归属和恢复成本，当前不优先。表名前缀是管理约定，不是数据库安全隔离。

轻量扩展可采用 (owner_id, record_id, plugin_id, extension_key) 定位的版本化 JSON。明确输入 schema、大小和迁移规则；频繁筛选、排序、金额统计、唯一约束和跨实体引用应进入类型明确的字段/关系，不全塞 JSON，也不预先建设任意字段的 EAV 引擎。

SQLite 支持 JSON 函数，但它的 JSONB 是 SQLite 内部格式，与 PostgreSQL JSONB 不兼容，也不提供通用 O(1) 属性查找。当前更建议先评估可读的 JSON 文本，不把 JSONB 当成数据库选择已附带的性能保证。[SQLite JSON](https://www.sqlite.org/json1.html#jsonb)

API DTO 与数据库行分别定义。插件可以把内部多表组合成公开对象，但不把表名、磁盘路径和全部私有字段直接暴露给前端。跨插件使用版本化服务契约，避免直接修改对方表。

## 4. 事务与并发

需要原子完成的动作，例如创建订阅记录、保存规则、挂接附件及写入待处理任务，使用同一个数据库连接和事务上下文。服务之间传递受控事务能力，不各开一个“看似同名”的独立事务。

公共记录版本在同一事务中更新。不同插件修改同一记录时先检查版本，冲突明确返回；未来若拆成分项版本需同步修改接口契约。文件上传、网络请求和 AI 调用不放在同步事务内部。

提交后再发送 UI 变化事件。必须在重启后继续执行的作业先在事务中登记，由消费者重试并去重；不依赖内存事件恰好成功送达。外部系统副作用使用自己的幂等和补偿策略，数据库回滚不能撤销已发送的外部动作。

## 5. 持久化契约与迁移

工具主线见 [已确认数据访问方案](../../current/storage/data-access-baseline.md)，版本账本、依赖、维护独占与失败恢复的详细建议统一维护在 [核心与插件迁移提案](../storage/plugin-migrations.md)。以下仅保留插件侧责任概览。

建议插件声明：稳定 ID、数据 schema 版本、所需核心/依赖版本、归属表与索引、顺序迁移、记录关联、附件引用、搜索贡献、删除恢复规则及导出信息。迁移元数据由公共服务持久保存，不随插件停用消失。

迁移由后端协调，先验证兼容与备份，再停止相关写入、执行并校验；记录迁移编号、校验摘要和执行结果。插件版本、数据库 schema 版本、每条扩展数据版本和 API 契约版本分别管理。

常规迁移优先可事务完成；需要分批回填或外部文件处理时声明阶段、恢复点和失败处置，不能假装全部原子。SQLite 的表结构修改能力随版本变化，必要重建表时遵循官方流程并检查外键、索引、触发器及视图。[SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html)

迁移失败时不激活依赖新结构的插件，不假装 schema 已升级；对核心数据完整性有影响时阻止相关写入。回退优先使用经验证的兼容路径或恢复备份，不自动运行可能丢数据的降级脚本。HMR 或普通 dispose 不执行破坏性迁移。

## 6. 停用、卸载与数据保留

用户已确认插件卸载默认保留数据；以下同时列出尚需细化的交互与持久契约。

| 操作 | 推荐行为 |
| --- | --- |
| 停用插件 | 关闭入口和运行资源，保留业务表、记录与文件；核心仍能展示通用信息 |
| 移除插件代码 | 默认保留数据和持久契约，标记扩展不可用；未知 schema 不直接编辑 |
| 重新安装 | 校验数据与代码版本兼容，必要时受控迁移；不自动重新触发所有旧任务 |
| 清除插件数据 | 独立、明确说明范围的操作；先检查公共记录、其他插件及文件引用，再确认处理 |

附件引用必须经公共文件服务登记，即使引用来自插件私有业务实体，也要有持久的保留关系，不能仅把文件 ID 藏在 JSON 中。否则核心无法判断是否安全回收文件。

备份覆盖活跃、停用及卸载后保留的数据、附件引用和迁移材料；不能只调用正在运行的插件来决定备份范围。插件额外文件需有持久清单并遵守对象保留协议，详见 [备份恢复](../storage/backup-recovery.md)。

回收站由公共记录状态控制，业务查询和执行共同遵守；插件不可用时仍应保留记录、业务数据和文件。彻底删除所需关系尽量通过持久声明与外键表达；需要插件专用清理而当前不可执行时，应明确阻止或标为待清理，不能先删除记录再让数据失联。

未来第三方插件可能拥有数据库所在进程的权限；上述服务和命名空间是工程契约，不提供恶意代码沙箱。隔离执行及外部插件授权需另设专题。

## 7. 待定与验证

查询已选 Drizzle SQL 风格 API + better-sqlite3，Kit 辅助生成迁移，后端采用 Recorder 统一命名空间账本与受控 SQL 执行适配。具体版本、迁移包格式、账本字段和适配实现仍待细化，见 [迁移机制提案](../storage/plugin-migrations.md)；不能因方便类型生成就让插件自行掌控核心表和连接设置。

待验证：正式业务中的同事务回滚、跨用户引用拒绝、并发版本、迁移失败恢复、未知插件数据保留、插件停用时的附件回收、删除恢复与重新安装。具体表结构和扩展契约仍为提案。隔离探针已验证部分事务与卸载保留行为，范围见 [工程基线](../../current/development/engineering-baseline.md)，不能代替本提案完整验收。
