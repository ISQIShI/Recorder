# Recorder 身份认证与多设备接入提案

状态：本地账号与后端可撤销会话已确认；认证库、凭据载体细节和登录交互未选定。更新日期：2026 年 10 月 25 日；本页认证技术资料核对日期：2026 年 10 月 24 日。确认范围见 [API 与认证主线](../../current/architecture/api-auth-baseline.md)。

阅读时机：登录、会话、设备管理、凭据保存、权限和未来账号扩展相关工作。接口入口见 [统一 API](../interfaces/unified-api.md)，连接和 TLS 边界见 [部署接入](../operations/deployment-access.md)。

## 1. 已确认前提与推荐

用户已明确：**同一后端先只供自己使用，保留以后增加账号的空间**。当前不建设团队、协作编辑或公开注册产品；也不因只有一个用户就把所有设备永久视为同一个凭据。

已确认基础为 **本地账号 + 后端可撤销会话**；Web Cookie 与原生端独立 Bearer 凭据继续作为配套推荐。数据模型建议从一开始保留用户归属，后续增加账号不必从全局资料库中猜测归属。

这里的“本地账号”指由当前 Recorder 后端自行管理的账号；后端部署在云服务器时也适用，不是 Windows 系统账号或各客户端分别保存一套账号。

| 方向 | 优点 | 成本与当前判断 |
| --- | --- | --- |
| 本地账号与服务端会话 | PC 离线可登录，云服务器也适用，可查看和撤销设备会话 | 基础方向已确认；口令与会话恢复机制待细化 |
| 已登录设备确认新设备 | 少重复输入口令，适合手机扫码和添加桌面端 | 需要短时授权请求、确认及防重放；建议作为便捷入口，详细协议待定 |
| Passkey 或外部 OIDC | 可改进登录体验，或接入已有身份系统 | 需处理域名/来源、设备支持、账号关联和外部依赖；留作后续扩展 |
| 所有客户端共用一个长期 API Key | 初始调用简单 | 无法清楚区分设备或单独撤销；不推荐作为日常登录体系 |

身份“怎样证明”与会话“怎样保持”分开设计。新增登录提供方应映射到同一内部 userId，不让插件各自创建互不相认的用户表。

## 2. 最小身份模型

| 概念 | 建议含义 |
| --- | --- |
| 后端实例 | 一份独立后端及其资料库的标识，持久保存，不随普通重启变化 |
| 用户 | Recorder 内部账号；当前只有 owner，数据仍有明确归属 |
| 安装实例／客户端登记 | 一次应用安装或浏览器资料环境的登记，用于显示名称和设备能力；不是登录凭证 |
| 会话 | 用户在某客户端获得的一次可撤销授权，带有效期和状态 |
| 凭据 | Cookie、访问令牌、刷新令牌等验证材料，关联会话；不能用 deviceId 替代 |
| 推送登记 | 渠道与 token，绑定用户和设备，用于投递；不是 API 访问令牌 |

手机重装可产生新安装实例，同一设备可能有多个会话；浏览器环境也不必被伪装成稳定硬件设备。允许用户命名和移除设备，避免用硬件指纹作为账号身份。

记录、附件、上传、任务、幂等结果、提醒和插件数据均需要归属边界。ownerId 从已认证上下文确定，不信任请求任意指定的用户标识。当前 owner 可兼任实例管理员，后续业务资料访问和实例管理权限再逐步分离；本轮不提前引入团队角色体系。

## 3. 首次初始化与日常登录

首次 owner 建立应由有后端主机访问权的人，通过本机或受保护的运维流程完成。可采用短时一次性初始化凭据，成功后关闭初始化入口；不能把“第一个从网络打开页面的人”自动设为管理员。PC 本机调用也不免除认证，环回地址不是用户身份。

建议基础登录使用本地账号口令：Web 经后端登录接口建立 Cookie 会话；Recorder 自有 Windows/Android 客户端可经受控登录界面建立各自设备会话，登录后不保存口令。只有这类第一方客户端处理自身后端的口令，第三方插件或外部应用不复用该接口充当授权平台。

口令使用成熟库的带盐密码哈希，优先评估 Argon2id，参数在目标运行环境测定；高熵随机令牌的摘要保存与口令哈希是不同问题。登录需要失败次数与速率控制，恢复流程须验证主机管理权限或预设恢复材料，不能依靠知道账号名即可重置。[OWASP 密码存储](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

为减少添加设备时重复输入口令，可以增加配对：新设备发起短时请求，已有登录会话确认目标后端、设备与权限，再将凭据交付给请求方。二维码或人类可读短码仅用于定位和确认请求，不携带长期令牌；请求方需另持有不可猜测的取回凭据，授权限定有效期、次数和用途。扫码本身不代表已授权。

配对暂未定实现库；如引入 OAuth 设备授权，应按 RFC 8628 完整实现和核验，不把简化扫码过程宣称为标准 OAuth。该标准主要面向输入受限设备，Recorder 是否采用应结合实际交互选择。[RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html)

未来接入 OIDC/OAuth 的原生登录时，采用系统浏览器和授权码 + PKCE，正确校验回调与发起方，不把提供方密码输入嵌入式 WebView，也不在公开客户端内嵌可保密的 client secret。[原生应用授权规范](https://www.rfc-editor.org/rfc/rfc8252.html)

## 4. 会话与令牌选择

| 方案 | 取舍 | 推荐 |
| --- | --- | --- |
| 随机不透明令牌，后端查询会话 | 容易撤销、更新权限和列出设备；每次需要会话状态查询 | 当前集中后端优先采用 |
| 自包含 JWT | 适合某些分布式验证；需管理签名密钥、受众和有效期 | 当前没有无状态验证的明确收益，单独撤销通常仍需状态，不优先 |
| 把完整会话放进加密/签名 Cookie | 减少服务端会话读取 | 单会话撤销和即时权限变化仍需额外机制，不作为本轮首选 |

建议会话状态持久保存在后端 SQLite，由认证服务管理。Cookie/令牌只作为随机标识，不承载可被客户端自行修改的用户权限；使用密码学随机源，敏感令牌按适配方案保存摘要而非明文日志。OWASP 建议客户端会话标识不包含身份信息，实际含义保留在服务端。[会话管理依据](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

原生端可采用短时访问令牌与可轮换刷新令牌，二者都关联可撤销会话。具体时长待定；后台任务使用同一个会话协调器刷新，避免多个上传任务同时消耗同一刷新令牌。轮换、重放检测及刷新响应丢失的恢复必须一起设计；失败时要求重新登录，不能无限重放旧凭据。OAuth 场景需遵循相应刷新令牌安全要求。[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

单台设备退出撤销该会话及相关刷新凭据；移除设备还应停用其推送登记。修改口令、账号恢复和“退出所有设备”分别定义撤销范围。对在途业务请求，撤销不等于回滚已提交事务。

## 5. 三端如何保存与使用凭据

| 客户端 | 推荐持有者 | 业务请求方式 | 边界 |
| --- | --- | --- | --- |
| Web | 浏览器管理 HttpOnly 会话 Cookie | 同源请求自动携带 Cookie | Vue 不读取会话秘密，不把长期 token 存入 localStorage |
| Windows | Electron 主进程的会话模块 | Authorization: Bearer，经 IPC 为 UI 服务 | 使用系统支持的安全存储保护落盘凭据；不向 renderer/UI 插件公开刷新令牌 |
| Android | Kotlin 会话与后台任务模块 | Authorization: Bearer，经 Capacitor 供 Vue 使用 | 凭据密文存应用私有区域，密钥由 Android Keystore 管理；不放进 WebView 存储 |

Electron safeStorage 使用平台密钥能力，但保护范围因系统而异，不能承诺隔绝同一系统用户下的所有进程。Android Keystore 主要保存和使用密钥，并不是直接把任意 token 字符串存进去；应用需配套加密与生命周期处理。[Electron safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) · [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

Android 凭据解锁策略需兼顾后台上传和提醒计划更新：若每次使用都要求生物认证，锁屏后台任务会受阻。默认保护方式及需要用户解锁的操作另定。退出登录后清除可用凭据、停止相关任务并暂停待提交队列；未提交内容如何保留或由用户删除需清晰提示，不能改投另一账号。

## 6. Cookie、CSRF 与浏览器来源

推荐 Web 与 API 同源部署。HTTPS 下会话 Cookie 使用 HttpOnly、Secure、合适的 SameSite，优先使用满足条件的 host-only / __Host- 约束；不为了前后端源码分目录而强行使用不同域名。

Cookie 会随浏览器请求自动发送，因此写操作需要成熟的 CSRF 防护并核验 Origin 等上下文；登录、退出和配对确认也应纳入。SameSite 与 CORS 不能独立代替认证和 CSRF 防护，GET 不执行业务修改。[OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

Bearer 接入与 Cookie 接入分别校验，再映射为统一身份。若一个请求同时携带不同身份的凭据，拒绝歧义而不是悄悄选择其中一个；原生端通常不附带 Web 会话 Cookie。没有 Origin 的请求不自动可信，仍需要有效凭据。

确需跨源 Web 部署时，只允许明确来源，分别配置预检和凭据策略；不使用反射任意 Origin 的方式解决跨域。Web UI 也可能受浏览器混合内容和本地网络访问限制，不把远程 HTTPS 网页直连任意 PC HTTP 服务作为默认方案。

仅本机环回 HTTP 的专用模式需要独立 Cookie 配置和验证，不能把 Secure Cookie 的 HTTPS 配置原样套用，或把本机例外扩大到 LAN/公网。细节见 [部署提案](../operations/deployment-access.md)。

## 7. 权限与插件

建议请求身份上下文包含 userId、sessionId、已验证的设备绑定和允许操作，不把 UI 传来的权限列表当依据。基础权限可按记录读写、附件、提醒、设备及实例管理划分，插件使用带命名空间的操作权限；字段和权限名仍是提案。

插件公开操作、文件下载、事件订阅、任务结果和幂等结果都走同一授权服务。业务插件可额外校验自身资源，不自行维护一套“只要有插件 token 就放行”的认证。身份服务不可用时拒绝受保护请求，不降级为匿名管理员。

设备支持剪贴板或通知，是能力信息；用户是否允许该操作，是权限；后端是否提供相应插件，是业务可用性。三者分开检查。后端推送不能授权任意读取手机文件，同一个 renderer 的 UI 插件也不会因为自报 pluginId 就获得可靠隔离。

后端 Cordis 插件属于受信任的进程内代码，权限注册不是进程沙箱。未来接入不可信第三方插件时另行设计隔离。AI 或自动化如需外部接入，可使用独立、可撤销且限定操作范围的凭据，不直接复用 owner 的完整会话。

## 8. 多设备与多后端

同账号的多台设备访问同一份后端数据；各自拥有会话、传输队列、设备能力、推送登记和提醒登记状态。删除一台设备不删除账号资料，也不退出其他设备。

客户端连接配置建议绑定实例标识、已验证服务地址和账号。实例标识帮助发现连错服务，不是证书或身份认证；URL 指向相同 instanceId 也不能据此忽略 TLS 错误或转发凭据。地址变更应重新确认可信来源，跨主机重定向不得无条件携带认证头。

换到另一后端后，旧 Android 队列、游标、附件缓存和提醒计划保留原归属并暂停或清理对应执行状态。PC 和云服务器各运行一份后端时，默认是两个独立资料库，不会因为登录名相同而自动同步或故障切换。

撤销设备后，服务端可立即拒绝新请求、终止在线事件并停止后续推送；无法立即抹除离线设备已经取得的文件、待提交输入或已登记提醒。客户端下次获知撤销时停止相关执行，不能把“退出设备”承诺成远程擦除。

整库恢复可能带回旧账号、授权和会话状态。当前建议使旧会话失效，通过受控恢复凭据重建访问，并引入恢复代次校正设备状态；具体契约未确认，见 [备份恢复提案](../storage/backup-recovery.md)。备份/恢复作为实例级管理能力授权，异地副本加密要求不代替访问控制，也不表示运行数据库已经加密。

## 9. 配套库与后续验证

Web 会话可以评估 @fastify/cookie + @fastify/session，并提供持久化 store；原生 Bearer 适配进入同一认证服务。不要把签名 Cookie 字符串直接当原生 token，也不要假设现成 Cookie 插件已包含完整设备授权、刷新与权限系统。@fastify/session 提供 store 接口，其默认内存 store 不适合生产；代理终止 TLS 时还要正确设置受信代理。[Fastify session](https://github.com/fastify/session)

具体认证组件与版本暂不锁定，实现前应比较维护状态、Fastify/SQLite 兼容和上述生命周期能力，优先采用成熟实现，不自行发明密码学或宣称一个简化流程已符合 OAuth。

需要验证：初始化只能完成一次、各端登录与续期、并发刷新、单设备撤销、跨账号访问拒绝、CSRF、代理下 Cookie、事件连接撤销、设备换账号和队列归属。本轮只有研究和文档，尚未执行这些测试。
