# Recorder 备份工具历史比较

状态：选型讨论已结束，用户于 2026 年 10 月 25 日确认 restic。本文保留选择前的比较语境，正文中的“推荐／未选定”不是当前状态。原官方资料核对日期与归档日期：2026 年 10 月 25 日；没有安装或验证工具。

阅读时机：追溯 restic 选择理由或实际约束变化需重新评估工具时。日常工作读 [已确认备份主线](../../current/storage/backup-baseline.md)；未冻结的实现建议已提炼到 [restic 集成设计](../../design/storage/restic-integration.md)，一致性与文件保护见 [备份恢复设计](../../design/storage/backup-recovery.md)。不默认阅读本篇中的旧集成提案。

## 1. 推荐结论与判断前提

当前推荐顺序：**restic 优先，Kopia 为主要备选；Duplicati 适合偏向独立备份应用的场景，BorgBackup 适合 Linux/SSH 运维环境。rclone 作为可选传输配套，不作为完整备份引擎的等价替代。**

这是结合 Recorder 的架构作出的判断：Windows 与 Linux 后端都需要运行，备份入口和任务状态由 Recorder 提供，Cordis 管理扩展，数据一致性已由统一恢复集合定义。我们更需要可控的备份执行工具，而不是必须另外部署一套备份管理界面。下述判断不构成速度、内存、稳定性或恢复成功率的实测排名。

## 2. 核心能力对比

| 工具 | Windows / Linux | 加密与异地目标 | 增量与去重 | 保留与空间回收 | 对 Recorder 的适配判断 |
| --- | --- | --- | --- | --- | --- |
| restic | 两者均有原生程序 | 客户端加密；本地、SFTP、对象存储等 | 按内容分块复用，同库多次快照共享数据 | 显式 forget 选择快照，prune 回收未引用数据 | 单可执行文件、CLI 和已记录的 JSON/退出码，适合作为首个受控适配器 |
| Kopia | 两者均有 CLI，也有 KopiaUI | 客户端加密；本地、NAS、SFTP、对象存储等 | 内容分块、仓库级去重，支持压缩 | 按策略过期、快照 pin、仓库维护与垃圾回收 | CLI 可独立使用；策略、维护所有者与可选服务需与 Recorder 协调，作为主要备选 |
| Duplicati | 两者均支持，含 GUI/CLI 形态 | 支持客户端加密与多种本地/远端目标，须验证实际配置启用加密 | 固定大小块去重、压缩与增量上传 | 按时间/版本/自定义规则删版本，再 compact 回收 | CLI 不必常驻服务，但有每个备份任务的本地数据库；使用 GUI/Server 还需协调其管理状态 |
| BorgBackup | 核对的 stable 1.4 系列以 Linux 等为主；Windows WSL/Cygwin 标为实验性 | 可启用客户端加密；1.4 主线以本地/SSH 仓库为重点 | 内容定义分块、仓库内去重 | prune 删归档，compact 才回收空间 | Linux/SSH 可用；当前不优先作为 Recorder 两平台统一工具 |

依据：[restic 平台与功能](https://restic.net/)、[Kopia 功能](https://kopia.io/docs/features/) 与 [安装形态](https://kopia.io/docs/installation/)、[Duplicati 平台](https://docs.duplicati.com/getting-started/installation) 与 [架构](https://docs.duplicati.com/technical-details/architecture-premises)、[Borg stable 能力](https://borgbackup.readthedocs.io/en/stable/)。

所有工具都必须消费 Recorder 已固定的恢复集合或受保护的文件视图。它们扫描活跃目录、支持 VSS 或产生“snapshot”，不自动证明数据库、附件、配置和插件数据属于同一恢复点。恢复后是否可以直接启动业务，仍由 Recorder 的兼容和设备对账决定。

## 3. restic：优先适配的方向

主要优势是工具边界清晰：Recorder 提交任务，工具执行备份、列举、复制、校验和恢复，退出后无需保留一个额外备份服务。官方为许多命令记录 JSON 输出和退出码；backup 有按行 JSON 状态消息，适合转成 Recorder 的作业进度。[restic 脚本接口](https://restic.readthedocs.io/en/stable/075_scripting.html)

代价是 Recorder 需要负责调度、凭据、取消、状态恢复、保留保护和 UI。并非所有命令及错误都输出同一种 JSON；兼容新增字段/消息类型，未知退出码不能按成功处理。工具成功也不替代清单核验，部分文件读取失败产生的快照不能标成完整恢复点。

restic 的仓库加密也适用于本地仓库。因此若后续选择“两份副本都由 restic 管理”，本地副本也将加密，需要把本地与异地的解密材料都纳入恢复方案；当前用户仅明确要求异地加密，不能在工具尚未选定时写成已决定本地加密。[restic 仓库初始化与口令](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)

保留分成两个动作：forget 移除快照，prune 才释放未被引用的块。prune 有仓库锁与维护成本，不能默认每次备份结束就立刻压缩清理；应与复制、恢复和检查协调。[restic 保留机制](https://restic.readthedocs.io/en/stable/060_forget.html)

**特别处理临时导出路径。** restic 默认按主机和源路径分组套用保留策略。如果每次使用新的随机路径，可能形成许多互不淘汰的分组。建议使用稳定的来源标识，或由 Recorder 限定实例/数据集范围后计算明确的候选快照 ID；不要把唯一 backupId 标签作为每次不同的保留分组，也不要为省事无范围地清理整个仓库。具体路径与分组约定待定。[分组规则](https://restic.readthedocs.io/en/stable/060_forget.html#removing-snapshots-according-to-a-policy)

## 4. Kopia：功能完整的主要备选

Kopia 同样可以只调用 CLI，不要求额外界面或服务。它提供内容去重、压缩、分层策略以及可选的 GUI/服务形态；若以后希望用户能脱离 Recorder 使用独立界面管理备份，这些能力更有吸引力。[Kopia 概览](https://kopia.io/docs/)

snapshot create 提供 JSON 结果、source 覆盖和 pin 等能力。它们可分别映射到 Recorder 的结果解析、稳定数据集标识和“升级前/正在复制的恢复点保护”；但不能据此假定其所有命令具有与 restic 相同的流式进度和失败语义。[Kopia snapshot create](https://kopia.io/docs/reference/command-line/common/snapshot-create/)

需要额外明确策略和维护责任：哪些快照可以过期、自动维护由哪个 user@host 执行、离线主机更换后如何接管。官方维护机制有单一维护所有者和安全等待规则，删除快照不保证立即回收全部字节。Recorder 不应为立即显示释放空间而关闭安全等待，也不能只关闭维护却不安排替代执行。[Kopia 维护](https://kopia.io/docs/advanced/maintenance/)

因此它的相对成本主要是要映射更多策略与仓库状态，不是无法集成或必须常驻。具体 API/CLI 版本、复制到第二仓库的方式及保留行为仍需单独验证。

## 5. Duplicati 与 Borg：适合不同约束

### Duplicati

Duplicati 提供自己的备份配置、界面和任务管理，也允许 CLI 在没有 Server 实例的情况下执行。CLI 仍需要明确每个任务的 dbpath 等本地状态；如果使用 Server，还要管理另一套服务、配置和授权，不能直接把其接口当 Recorder 公共 API。[Duplicati CLI](https://docs.duplicati.com/duplicati-programs/command-line-interface-cli)

其每个备份任务的本地数据库可从远端数据重建，丢失它不等于所有备份丢失，但重建是额外恢复步骤和耗时来源；Server 的配置数据库与这些可重建数据库是不同材料。不能把工具内部数据库与 Recorder 业务 SQLite 或迁移账本合并管理。[Duplicati 数据库](https://docs.duplicati.com/technical-details/database-versions)

官方当前文档已描述从 **2.3.0.0** 起支持多目标：先写首个目标，再复制到其他目标；并可在有警告时继续复制。这与本地加异地的需求相关，但该功能门槛不代表项目已选此版本，实施前还需核对所用发行包及其目标状态语义。Recorder 的完整性判定必须独立，不能把“有警告也已复制”显示成完整成功。[多目标说明](https://docs.duplicati.com/configuration-and-management/multiple-backup-destinations)

保留可按时间、数量和自定义规则执行；CLI 可将删除从备份步骤分离，之后还有 compact。若采用它，需要确保这些自动规则不会清掉等待异地复制或用于故障恢复的集合。[Duplicati 保留](https://docs.duplicati.com/configuration-and-management/retention-settings)

当前不优先的原因是其任务与本地状态适配成本，而不是缺少 CLI、加密、去重或多目标能力。

### BorgBackup

Borg 在 Linux/SSH 环境下提供仓库内内容分块去重和可选加密，但核对的 stable 1.4 文档将 Windows WSL/Cygwin 标为实验性。latest 文档目前属于 Borg 2 beta 开发线，不能用其中新增能力直接当成 stable 的生产支持或替项目选预发布版本。[Borg stable 安装](https://borgbackup.readthedocs.io/en/stable/installation.html)、[Borg 2 开发状态](https://borgbackup.readthedocs.io/en/latest/)

其 prune 与 compact 也分开，归档筛选范围须明确；支持 Linux 服务器并不意味着 Windows 本地后端获得同等简单的部署路径。[Borg prune](https://borgbackup.readthedocs.io/en/stable/usage/prune.html)

若将来只部署 Linux 后端且已有 SSH/Borg 运维环境，可以重新考虑；当前为两个平台分别建设两套备份工具，收益不足以抵消维护差异。

## 6. rclone、增量与两份副本

rclone 支持多种存储接口及 crypt，可在目标不被备份工具直接支持时作为传输配套。普通 copy/sync 加 crypt 不自动提供与 restic/Kopia 相同的块级去重、快照引用和保留机制；sync 还可能把源端删除传播到目标。当前不将它作为唯一备份引擎，也不在有原生目标适配时默认增加一层。[rclone 存储接口](https://rclone.org/overview/)、[crypt](https://rclone.org/crypt/)、[sync 语义](https://rclone.org/commands/rclone_sync/)

对 Recorder，增量的价值主要来自重复附件只保存一次，以及数据库快照中未变化块的复用。音视频原本已压缩，不能据工具支持压缩就承诺大幅缩小体积；数据库页面重排等也会影响去重，必须用实际资料验证。

统一集合不要求每次先生成一个全新的加密压缩大文件再交给备份工具。优先把清单、数据库副本和稳定的对象文件交给工具分块、压缩与加密，避免外层重新打包扰乱复用。每个恢复点在逻辑上完整，工具内部共享数据块；不要求用户手工拼接增量链。

若选择 restic，推荐优先验证“本地仓库提交完整快照 → 按明确快照 ID 复制到独立异地仓库”。官方提供 copy；目标仓库使用匹配的分块参数有助于复制快照的去重，创建时就需要规划，不能把它等同于共用密码或共享删除策略。[restic 仓库复制](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#copying-snapshots-between-repositories)

另一可行路线是同一封存输入分别写入两个目标，代价是重复扫描和读取；两者的断线恢复、空间、密钥隔离和性能需在选型后比较。所有路线都保存 Recorder backupId/清单摘要到工具仓库中的可恢复材料，并分别记录目标仓库身份和原生快照 ID；不能假定两个目标原生 ID 一定相同，也不以不限定范围的 latest 代表当前任务结果。

本地快照在异地未完成前需要保留保护。工具级去重仓库的原始目录，不应在其写入或清理期间被普通文件同步随意镜像；优先工具支持的复制或经验证的一致导出。异地应有自己的保留策略，不能仅因本地清理就隐含删除唯一灾难恢复点。

## 7. 与 Cordis 后端的职责边界

推荐采用 **现有 Cordis 服务 + 一个工具适配插件 + 受控子进程**；不引入第二套插件框架，不为几个命令提前实现所有工具的通用引擎。

| 模块 | 责任 | 不承担的责任 |
| --- | --- | --- |
| 恢复集合服务 | 快照、清单、插件材料与附件保留保护 | 不实现块级去重和仓库加密算法 |
| 备份协调服务 | 持久任务、目标状态、重试、复制依赖、保护规则与恢复流程 | 不把工具进度直接当完整备份成功 |
| Cordis 工具适配插件 | 将备份、列举、校验、复制、恢复和清理计划映射到选定工具 | 不自行绕过业务一致性、开启第二套用户调度 |
| 受控进程执行 | 固定可执行文件、参数数组、凭据注入、输出解析、超时/取消、退出与崩溃对账 | 不提供接受任意命令或原始仓库凭据的前端入口 |
| 工具仓库 | 原生快照、共享数据块、加密和工具级完整性机制 | 不管理 Recorder 用户会话、插件 schema 或手机提醒 |
| REST/API 与 SSE | 管理操作授权、作业查询与进度；三端复用 | 不让客户端直连工具管理端口或直接执行备份程序 |

以上名称是职责示意，接口尚未冻结。备份协调状态、工具仓库事实和数据库迁移账本分别管理；任务状态丢失时可依据仓库中的清单/ID 对账，不能依赖只存在于待恢复业务库中的一张映射表才能找到备份。

按当前推荐的 TypeScript/Node 后端方向，优先调用官方可执行程序，通过参数数组启动并禁用 shell 解释；Windows 使用隐藏子进程，不弹出额外终端。工具作为独立进程也不表示整个 Cordis 插件已进入安全沙箱。后端语言、二进制分发方式和具体版本继续按技术状态确认。

### Windows PC 与 Linux 服务器

两种部署共用恢复集合、任务状态和 API，按平台提供对应可执行程序与路径适配。备份能力安装在后端所在设备，Electron、Web 与 Android 只是控制入口；云服务器备份不要求在手机或 Windows 客户端再安装同一工具。

| 部署 | 建议重点处理 |
| --- | --- |
| Windows PC 后端 | 后端服务账号对资料库和外接盘的访问权限、盘符变化、中文/长路径、休眠中断、工具版本替换；目标盘缺席时标为不可用，不悄悄改写到系统盘同名目录 |
| Linux 服务器后端 | 非交互账号、文件权限、持久挂载、磁盘容量与工具架构；容器重建或 hostname 改变时，维持清晰的数据集身份和保留范围 |
| 两平台之间恢复 | 先恢复到隔离目录，验证文件名、大小写、权限和路径映射，再重建目标平台的程序与插件依赖；备份文件可读取不代表整个运行目录可直接跨平台启动 |

调度属于后端。PC 关机期间不能新生成备份，重新上线后是否补跑、如何限制积压和带宽仍需设计；服务器长期运行也不等于备份一直成功，两者都显示最近完整本地副本及异地副本的实际数据时间。上述平台事项是待验证清单，不是已经测试通过的兼容结论。

### 生命周期、取消与故障

- 适配器以 Cordis 服务注册并声明依赖；基础存储、文件保护或凭据服务未就绪时，不开始任务。HMR/卸载先停止接新任务，再显式等待完成或取消，不在普通 dispose 中执行 forget/prune 或删除副本。
- 单个仓库的备份、copy、校验、恢复和回收按兼容规则协调；初期可保守串行管理。保留工具原生锁；不能看到锁冲突便自动 unlock、break-lock 或重建仓库。
- 取消先请求正常退出并等待确认。进程被终止不等于远端没有提交，后端崩溃重启也先按 backupId/原生快照/清单对账，再决定重试，避免产生无主副本或重复执行清理。
- 输出按行/流式读取并有界保存，错误、部分成功和未知结果明确区分。restic 的 JSON 与退出码规则按锁定版本适配；其他工具不能直接套同一结果协议。
- Cordis 停用不删除仓库、缓存、恢复密钥或持久任务。只有确认已无读取进程且任务可恢复/已放弃，才释放对象保留；不能让子进程仍在读文件时先清理其输入。

### 凭据、发布与恢复入口

仓库口令与云凭据放在后端受保护配置/秘密入口，避免命令行和日志泄漏；环境变量也不应被当作对同权限进程绝对保密。固定可执行路径和允许参数，拒绝客户端提交命令片段或用任意脚本替换工具。具体密钥保存方式未选。

二进制版本、支持的命令/输出、仓库格式和发布来源一起登记，校验官方发行材料。升级时既验证旧仓库可读取，也测试干净机器恢复；不自动追随 latest，更不未经规划升级到无法由现有恢复工具读取的格式。是否随 Recorder 安装包分发以及相应发布义务留到实际选型时核对。

若 Recorder 业务库损坏，最小维护入口仍应能调用工具、读取清单并恢复到隔离目录。恢复操作先解析和校验备份，再按已有方案处理插件兼容与设备对账，不直接启动备份中携带的任意代码。

## 8. 保留策略与验证重点

建议由 Recorder 生成“哪些恢复集合仍受保护、哪些可以删除”的计划，工具负责执行自身快照删除与块回收。原生自动策略如需启用，必须能表达这些保护条件并由同一配置来源管理；不要叠加两个互相看不见的删除计划。份数和期限仍未确定。

工具选型后的验证至少覆盖：Windows/Linux 中文与长路径；大小写及权限差异；大量小文件和大视频；变动数据库副本的实际去重；两目标复制失败与重试；主机/来源路径变更后的保留分组；部分成功；进程退出与后端重启竞争；升级前 pin 与异地待复制保护；仓库检查、真实隔离恢复和工具版本升级。

结果分别报告耗时、业务响应影响、扫描/传输字节、磁盘峰值、恢复耗时和完整性，不用某个工具自己的扫描速度代表整条 Recorder 备份流程。
